# Worked example: Tokopedia order 579011466600023489

How one order travels from the raw Excel export to `t_order` / `t_order_detail`. All numbers below are
taken from the files produced by the pipeline (`run_all.sh`, steps 1–7).

**Result in one line:** 3 raw lines (3 Tokopedia SKUs) became 4 detail rows, because two sold SKUs are
bundles that were broken down into their components.

---

## 0. The raw data

File `raw/tiktok_tokopedia/Tokped_Order_20220101_20251230.xlsx`, sheet `OrderSKUList`, Excel rows 85530–85532.
The export has one row per ordered SKU:

| Excel row | SKU ID (platform SKU) | Seller SKU (as exported) | Product | Qty | Unit price | Seller discount | Subtotal after discount |
|---|---|---|---|---|---|---|---|
| 85530 | 1731525364105577516 | *same text as product name* | Kitten in Gravy Wet 12X85gr - 1 Box | 1 | 272,950 | 40,942 | 232,008 |
| 85531 | 1731525383076545580 | *same text as product name* | Kitten in Loaf Wet 6x85gr | 1 | 397,500 | 59,625 | 337,875 |
| 85532 | 1731525383028900908 | *same text as product name* | Mother & Babycat Mousse Set Of 6 100g | 1 | 128,628 | 19,294 | 109,334 |

Order-level fields repeat on every row: Order ID 579011466600023489, Purchase Channel `Tokopedia`, status
`Selesai`, created `14/07/2023 17:16:25`, paid `17:16:28`, shipped `15/07/2023 21:57:01`, delivered
`17/07/2023 13:28:43`, `Order Amount` 719,617, `Original Shipping Fee` 54,000, warehouse `WH cakung (Temp)`,
`Pengiriman standar`, GoPay, DKI Jakarta / Kota Administrasi Jakarta Selatan, buyer `A***ia J***ine`.

Things to notice already:
- In 2023 the seller never filled `Seller SKU`; the export shows the product name in that column. Only the
  platform `SKU ID` is a reliable key for this order.
- Money columns are plain numbers; timestamps are Jakarta wall-clock text (`DD/MM/YYYY HH:MM:SS`).

## Step 1 – Raw → `stg_tokopedia.csv`  (`step1_stg_tiktok_tokopedia.py`)

- Read all 8 files of `raw/tiktok_tokopedia/` with `calamine` (the openpyxl reader fails on these files).
- Header names are snake-cased exactly like the DDL (`SKU ID` → `sku_id`, `Seller SKU` → `seller_sku`).
- Row 2 of every file is a description row ("Platform unique order ID.") – dropped because its `Order ID` is not numeric.
- Rows are routed by `Purchase Channel`: `Tokopedia` → `stg_tokopedia.csv`, `TikTok` → `stg_tiktok.csv`.
- Rows identical in two overlapping files are kept once; the file/row of origin is kept in `source_file`, `source_row_no`.
- Sorted by `created_time` ascending, then `order_id`.

Our order = 3 consecutive rows in `stg/stg_tokopedia.csv`, `source_row_no` 85530–85532, values still **text**.

## Step 2 – `stg_*` → `stg_unique_sku.csv`  (`step2_extract_unique_sku.py`)

Every stg file is normalised to a common line layout (`common/normalize.py`):

| standard field | Tokopedia/TikTok source column |
|---|---|
| order_no | Order ID |
| created_at | Created Time (`%d/%m/%Y %H:%M:%S`) |
| seller_sku / platform_sku | Seller SKU / SKU ID |
| quantity, unit_price | Quantity, SKU Unit Original Price |
| seller_discount, platform_discount | SKU Seller Discount, SKU Platform Discount |
| shipping_fee, order_total | Original Shipping Fee, Order Amount |

Then one row per (marketplace, seller_sku, marketplace_sku) with the first/last time it was ordered.
Our three platform SKUs show up in 10 unique rows because the same listing was sold under different seller SKUs
over time, for example listing `1731525364105577516` (Kitten in Gravy BOX):

| seller_sku | first order | last order |
|---|---|---|
| *(product name text)* | 2023-07-14 17:16 ← **our order** | 2025-05-26 |
| `40580010` | 2025-05-27 | 2025-05-28 |
| `TKP_40580010` | 2025-05-29 | 2026-04-19 |
| `37/020100401C` | 2026-04-22 | 2026-09-30 |

`dq_note = seller_sku_changed` marks this listing as having a SKU history.

## Step 3 – Unique SKU → SKU master  (`step3_cleanse_sku_master.py`)

1. **Clean the seller SKU** (`TKP_40580010` → `40580010`; product-name text is only upper-cased).
2. **Union-find**: every cleaned SKU seen on the same listing is the same product, so all four values above, plus
   the later codes, collapse into **one SKU master**.
3. **Survivorship**: master code = the most recently introduced SKU.

Result for our three listings:

| platform listing (`m_platform_sku`) | platform_sku_id | → sku_id | master_sku |
|---|---|---|---|
| 1731525364105577516 | 889 | 382 | `37/390109905L` |
| 1731525383076545580 | 404 | 181 | `37/390109902K` |
| 1731525383028900908 | 485 | 214 | `37/390109902F` |

`m_sku_alias` keeps every old code (e.g. `40580010`, `37/020100401C`, the product-name text) pointing to sku_id 382,
and `m_sku_history` records the seller-SKU changes of the listing.

## Step 4 – Bundle price check  (`step4_bundle_price_check.py`)

Review only. For each bundle in `bundling_master.csv`: bundle price vs. Σ(component price × qty); a gap above 10%
of the lower price is flagged (single-component gaps are marked `pass`). This does not change the order.

## Step 5 – Bundle SKUs  (`step5_bundle_sku.py`)

All three sold SKUs are bundles in `bundling_master.csv` (`bundle_flag = True`). Rules applied before `m_sku_bundle`
is written (`common/bundle.py`):

- **Recursive PCS ↔ BOX pairs** (PCS lists BOX with blank qty, BOX lists PCS ×12): keep the row with the quantity.
- **Bundle inside a bundle**: flatten down to leaf components, multiplying quantities.

`m_sku_bundle` for our SKUs:

| bundle (sku_id) | seq | component | qty | component price | dq_flag |
|---|---|---|---|---|---|
| 382 `37/390109905L` | 1 | 944 `37/020100201A` (Kitten Instinctive 12X85G PCS) | **12** | 22,542 | `flattened` |
| 382 | 2 | 886 `37/B376929208B` ([FOR GIFT] plastic container) | 1 | **0** (free gift) | `free_gift` |
| 181 `37/390109902K` | 1 | 953 `37/020100201C` (Kitten in Loaf 12X85G PCS) | 6 | 22,542 | |
| 214 `37/390109902F` | 1 | 908 `37/020100501A` (Babycat 24X100G PCS) | 6 | 21,875 | |

(`flattened` on 382: the master says BOX = 1 BOX-SKU, and the BOX-SKU is 12 × PCS, so the bundle is stored as
12 × PCS.)

## Step 6 – Raw lines → orders & details  (`step6_tx_tiktok_tokopedia.py`, `common/tx.py`)

**a. Parse** (text → typed): times to datetime, money to number, quantity to integer.
`line_key` has no marketplace line id here, so it is `<SKU ID>:<n-th occurrence in the order>`, e.g. `1731525364105577516:1`.
`gmv_1` (line gross value) = unit price × quantity.

**b. Resolve the SKU**: platform SKU ID → `m_platform_sku` → `sku_id` (fallback: cleaned seller SKU → `m_sku_alias`).
Here the product-name "seller SKU" is irrelevant, the platform SKU ID resolves it. All 3 lines are bundles.

**c. Break the bundle lines down** (quantity × component qty; value split by component price × qty):

| Line | Line gross | Component | Qty | Weight | Share | gmv_1 | Seller discount |
|---|---|---|---|---|---|---|---|
| 1 (BOX) | 272,950 | 944 PCS | 1 × 12 = 12 | 12 × 22,542 | 100% | **272,950.00** | 40,942.00 |
| 1 | | 886 gift container | 1 × 1 = 1 | 1 × 0 | 0% | **0.00** | 0.00 |
| 2 (Loaf) | 397,500 | 953 PCS | 1 × 6 = 6 | 6 × 22,542 | 100% | **397,500.00** | 59,625.00 |
| 3 (Mousse) | 128,628 | 908 PCS | 1 × 6 = 6 | 6 × 21,875 | 100% | **128,628.00** | 19,294.00 |

- The gift container is a free gift (`37/B…`, "B - …", no price in `bundling_price.csv`), so its price is 0 and the whole
  line value goes to the PCS component. If every component of a bundle had price 0 (gift-only bundles), the split falls
  back to quantity (`dq_flag = equal_split`, listed in `t_order_detail_dq.csv`).
- Rounding: parts are rounded to 2 decimals and the remainder goes to the last component, so the split always
  adds up to the original line.
- `unit_price` of a component = its allocated `gmv_1` / quantity; `unit_sold = quantity`.
- The `line_key` of a component gets `#<component_seq>`: `…516:1#1`, `…516:1#2`, `…580:1#1`, `…908:1#1`.

**d. Order header** (one row, grouped by order number, after the breakdown):

| column | value | rule |
|---|---|---|
| order_created_at | 2023-07-14 17:16:25+07 | earliest line; naive Jakarta time + `+07` |
| item_line_count | 4 | detail rows after breakdown |
| total_quantity | 25 | 12 + 1 + 6 + 6 |
| shipping_fee | 54,000 | order-level value repeated on each line → taken once (`GMV2_DEDUP`) |
| gmv_2 | 719,617 | `Order Amount`, taken once per order |

Note: `gmv_1` over the lines (272,950 + 397,500 + 128,628 = 799,078) is gross value before discounts;
`gmv_2` is the amount the order actually totals (after discounts, shipping fee and shipping discount).

## Step 7 – Merge into single files  (`step7_merge_transactions.py`)

Per-channel files are merged into `transaction/t_order.csv` and `transaction/t_order_detail.csv`:

- Orders are sorted by created time, then channel, then order number; `order_id` and `order_detail_id` are renumbered 1..N.
- `city` + `province` are replaced by `city_id` from `sku_master/m_city.csv` (Kota Administrasi Jakarta Selatan = 404).

## Checks that guarantee the result

- Σ `gmv_1` before and after the breakdown is unchanged (799,078 here); the script asserts it per channel.
- Σ quantity of non-bundle lines is unchanged; `(order_id, line_key)` is unique; every detail has an order.
- `item_line_count` / `total_quantity` of every order equal the count / sum of its detail rows.

## Data points to review for this order

1. **Free gifts**: components that are "B - …" / `37/B…` items (gimmick, sampling, box, voucher) have no price in
   `bundling_price.csv`. They are treated as free gifts with price 0 (`free_gift` in `m_sku_bundle.dq_flag`), so the bundle
   value is spread over the other components only. Here the plastic container takes 0 of the BOX line.
2. In 2023 the exported `Seller SKU` was the product name; matching relied on the platform SKU ID. Product names are
   kept in the SKU alias table for traceability only.
3. Bundle `37/390109902F` (Mousse Set of 6) is built from a *Babycat 24X100G PCS* component ×6; worth confirming the
   mapping in `bundling_master.csv` is intended.
